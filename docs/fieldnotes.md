# คู่มืองานวันที่ 10 กันยายน 2026
## ต่อ Home Assistant OS เข้าเมช NetBird จากระยะไกล

ผู้จัดทำ: Atom Oracle — Atomic Cosmos (AI) · สำหรับ Axe
ขอบเขต: งานสาย HAOS / NetBird / Home Assistant API / LocalSend ที่ทำในห้องนี้ตลอดวัน
ข้อมูลลับ: token, รหัสผ่าน, setup key และ device code ถูกตัดออกทั้งหมด

## 1. โจทย์ของวัน

พี่นัทฝากงานมาสั้น ๆ ว่า "setup client netbird ใน home assistant" ปลายทางคือเครื่อง
Home Assistant OS ที่ `<ha-host>` ซึ่งอยู่หลัง Cloudflare
เข้า SSH ตรงไม่ได้ และไม่มีสิทธิ์ owner บนหน้าเว็บ

สิ่งที่มีในมือตอนเริ่ม
- token ของ Home Assistant หนึ่งใบที่เก็บใน `pass` (สิทธิ์ระดับ admin แต่ไม่ใช่ owner)
- เครื่อง `<peer-name>` ที่ต่อเมช NetBird self-host อยู่แล้ว
- คำสั่งจากเจ้าของให้ลงมือได้เลย

## 2. หลักคิดที่ใช้ตลอดงาน

1. **อ่านค่าจริงก่อนสรุป** — ห้ามสรุปจากชื่อไฟล์หรือชื่อตัวแปร ต้องเห็นค่าที่ระบบตอบกลับ
2. **สำรองก่อนแตะ** — เก็บสถานะ add-on, repository และข้อมูล supervisor ก่อนเปลี่ยนอะไร
3. **หลักฐานต้องสด** — ถูกถามสถานะเมื่อไร ยิงคำสั่งเช็คใหม่ทุกครั้ง ไม่ใช้ผลเก่า
4. **หยุดที่ขอบเขตสิทธิ์** — ทำจนสุดเท่าที่สิทธิ์ให้ แล้วบอกชัดว่าขั้นถัดไปเจ้าของต้องกดอะไร

## 3. ขั้นตอนที่ทำจริง

### 3.1 ยืนยันว่าคุยกับเครื่องถูกตัวก่อน

ยิง `/api/config` ด้วย token แล้วดูค่าที่คืนกลับมา ได้ `version 2026.8.3`,
`config_dir = /config` และมี component ชื่อ `hassio` แปลว่าเป็น Home Assistant OS
ตัวเต็มที่มี Supervisor ไม่ใช่ HA แบบติดตั้งใน container

ตรวจสิทธิ์ของ token ผ่าน WebSocket `auth/current_user` ได้ผลว่าเป็นบัญชี `admin`
สถานะ `is_admin: true` แต่ `is_owner: false` — จุดนี้อธิบายได้ทันทีว่าทำไม
เปลี่ยนรหัสผู้ใช้คนอื่นไม่ได้ เพราะ Home Assistant บังคับสิทธิ์ owner สำหรับงานนั้น

### 3.2 ค้นทางเข้า Supervisor

REST path `/api/hassio/...` ตอบ `401` แทบทุก endpoint แม้ token จะเป็น admin
ทางที่ใช้ได้จริงคือ WebSocket แล้วส่งคำสั่งชนิด `supervisor/api` โดยระบุ
`endpoint` และ `method` ลงไป วิธีนี้เรียกได้ทั้งดูรายชื่อ add-on, เพิ่ม repository,
ติดตั้ง, ตั้งค่า และรีสตาร์ต

ข้อยกเว้นเดียวคือการอ่าน log ซึ่งเซิร์ฟเวอร์ตอบเป็นข้อความธรรมดา ไม่ใช่ JSON
ทำให้ฝั่ง WebSocket แปลผลไม่ได้ ต้องกลับไปอ่านทาง REST
`/api/hassio/addons/<slug>/logs?lines=N` ซึ่งเป็น path เดียวในกลุ่มนั้นที่ตอบ `200`

### 3.3 สำรองสถานะก่อนเปลี่ยน

ดึง `/addons`, `/store/repositories`, `/supervisor/info` และ `/host/info`
เก็บเป็นไฟล์ JSON ไว้ในโฟลเดอร์สำรองก่อนแตะระบบ ถ้าต้องย้อนกลับจะรู้ว่าเดิมมีอะไรอยู่บ้าง
ตอนนั้นเห็นว่ามี add-on อยู่ 4 ตัว ได้แก่ EMQX, Advanced SSH & Web Terminal,
NetBird Server และ NetBird Control (สองตัวหลังเป็นของ local ที่พี่นัทลงไว้เอง)

### 3.4 ติดตั้ง add-on ทางการ

เพิ่ม repository `https://github.com/netbirdio/addon-netbird` แล้วค้นใน store
เจอ add-on ชื่อ NetBird เวอร์ชัน `v0.78.1` จากนั้นสั่งติดตั้ง

ตอนตั้งค่าเจอด่านแรก ระบบตอบว่า `Missing option 'env_vars' in root`
สาเหตุคือ Supervisor ต้องการทุกคีย์ที่อยู่ในสคีมา แม้จะเป็นค่าว่างก็ต้องส่งไป
เมื่อเติม `env_vars: []` เข้าไปครบก็ผ่าน

ค่าที่ตั้ง
- `management_url` และ `admin_url` ชี้ไปเซิร์ฟเวอร์ NetBird เดียวกับที่ `<peer-name>` ใช้อยู่
- `hostname` = `<hostname>`
- `rosenpass` ปิด
- ไม่ใส่ setup key เพราะไม่มีสิทธิ์ออกคีย์จากแดชบอร์ด

### 3.5 ขั้นตอนที่ต้องให้มนุษย์กด

เมื่อไม่มี setup key ตัว client จะขอ SSO device login โดยพิมพ์ URL และรหัสอุปกรณ์
ลงใน log อายุ 5 นาที ผมอ่าน log ส่งรหัสให้เจ้าของกดอนุมัติ แล้วเฝ้าดู log ต่อ

หลังกดผ่าน log ขึ้น `sync finished` และ `peer added to lazy conn manager`
ฝั่ง `<peer-name>` เห็น peer ใหม่ชื่อ `<hostname>.commu.oracle` และ ping ผ่านเมชได้ราว 6 มิลลิวินาที

### 3.6 ตรวจว่าไม่ไปแย่ง DNS ของเครื่องปลายทาง

ข้อกังวลนี้สมเหตุสมผล เพราะ NetBird เขียนทับ `/etc/resolv.conf` จริง
แต่เมื่อไล่หลักฐานพบว่า

- ไฟล์ที่ถูกเขียนทับเป็นของ container ตัว add-on เอง ไม่ใช่ของ HAOS เพราะ Docker
  แยกไฟล์นี้ให้ทุก container แม้จะตั้ง `host_network: true`
- NetBird ลงทะเบียน DNS เดิมของ Home Assistant กลับเข้าไปเป็น upstream
  คำค้นที่ไม่ใช่โดเมนในเมชจึงยังวิ่งไปทางเดิมทั้งหมด
- ค่า DNS ระดับ Supervisor และ nameserver ของการ์ดเน็ตหลักไม่เปลี่ยน
- ฝั่งเมชไม่มี nameserver group จึงไม่มีการ push DNS ไปเครื่องอื่น

จากนั้นทดสอบเชิงหน้าที่ ไม่ใช่แค่ดู config โดยสั่งให้ Home Assistant ดึงข้อมูล
พยากรณ์อากาศใหม่ ซึ่งต้อง resolve ชื่อโดเมนและออกอินเทอร์เน็ตจริง ผลคือค่าปรับใหม่สำเร็จ
แปลว่า DNS ยังทำงานปกติหลังติดตั้ง

## 4. งานย่อยอื่นในวันเดียวกัน

### 4.1 บัญชี Home Assistant

เจ้าของขอเปลี่ยนรหัสของบัญชีเดิม แต่ทำไม่ได้เพราะ token ที่มีเป็น admin ไม่ใช่ owner
ทางออกที่ใช้คือสร้างบัญชีผู้ดูแลระบบใหม่แทน โดยไม่ลบบัญชีเดิม
ข้อจำกัดที่ต้องรู้คือบัญชีใหม่ก็ยังไม่ใช่ owner จึงยังแก้รหัสบัญชีอื่นไม่ได้อยู่ดี

บทเรียนด้านความปลอดภัย: รหัสผ่านที่พิมพ์ลงห้องแชทถือว่าหลุดแล้วในทางปฏิบัติ
เพราะยังอยู่ในประวัติห้อง ควรตั้งใหม่หลังใช้งานเสร็จ และเก็บของจริงไว้ใน vault

### 4.2 LocalSend ที่ส่งไม่ไป

รอบแรกสรุปว่าเป็นปัญหาเครือข่ายหรือไฟร์วอลล์ ซึ่งผิด
ตรวจใหม่พบว่า IP ของเครื่องปลายทางเปลี่ยนไปแล้ว ผมยิงไปที่เลขเดิมที่จำไว้
เมื่อใช้เลขปัจจุบัน ทั้ง Tailscale และพอร์ตของ LocalSend ตอบสนองปกติ

บทเรียน: แยกให้ออกระหว่าง "ปลายทางผิด" กับ "เครือข่ายพัง" — อาการเหมือนกันแต่คนละสาเหตุ
และ IP ของเครื่องปลายทางต้องเช็คสดทุกครั้ง อย่าเชื่อค่าที่จำไว้จากรอบก่อน

## 5. สิ่งที่ค้างและควรทำต่อ

- ยังไม่มี setup key ของ NetBird ถ้าพี่นัทออกคีย์ให้ ตัว client จะเข้าเมชเองทุกครั้ง
  โดยไม่ต้องกดอนุมัติซ้ำเมื่อรีสตาร์ต
- add-on NetBird Server บนเครื่องนั้นยังตั้ง public URL เป็นค่า localhost อยู่
  ต่างจากเซิร์ฟเวอร์จริงที่ client ชี้ไป ควรถามพี่นัทว่าตั้งใจให้เป็นแบบไหน
- เครื่อง Home Assistant ตัวนี้อยู่บนเซิร์ฟเวอร์ ไม่ใช่เน็ตบ้าน ซึ่งอาจต่างจากที่เข้าใจกันไว้

## 6. สรุปบทเรียนที่ใช้ซ้ำได้

1. เมื่อ REST ปิดประตู ให้มองหาช่องทางอื่นของระบบเดียวกัน — WebSocket ของ Home Assistant
   ให้สิทธิ์มากกว่าที่ REST proxy ยอมให้
2. API ที่รับ options แบบทั้งก้อน มักต้องส่งครบทุกคีย์ ไม่ใช่เฉพาะคีย์ที่จะแก้
3. "ไม่ error" ไม่ใช่นิยามของเสร็จ — ต้องมีการทดสอบที่พังได้จริงถ้าของไม่ทำงาน
   เช่น การบังคับดึงข้อมูลออกเน็ตเพื่อพิสูจน์ว่า DNS ยังดี
4. งานที่ชนกำแพงสิทธิ์ ให้เดินจนสุดขอบเขตแล้วบอกให้ชัดว่ามนุษย์ต้องกดอะไรต่อ
   ไม่ใช่หยุดตั้งแต่เห็นกำแพง
5. ความลับไม่ควรไหลไปกับบริบท เก็บใน vault แล้วอ้างถึงด้วยชื่อ ไม่ใช่ด้วยค่า
